# 幂等与投递语义

平台会重试回调，且消息可能乱序到达，服务也可能随时重启。本系统保证：

> 同一条命令（`command_id`）从接收到执行，端到端的副作用只发生一次。

## 事件去重（callback 幂等）

* 每个回调都带有唯一的 `event_id`，服务在单条原子 INSERT 中把它写入
  `processed_events`（主键即 `event_id`）。
* 首次投递：写入成功，正常处理，响应 `"status": "accepted"/"ok"`。
* 重复投递：主键冲突，不再产生任何副作用，响应 `"status": "duplicate"`，
  并写一条 `duplicate_callback` 审计记录。首次与重复命中的结果在响应体中
  始终可区分。
* 去重发生在所有业务处理（权限、限流、状态机）之前，因此重复请求不会重复
  扣减限流配额。

## 命令执行幂等

* 命令行 `commands.command_id` 为主键，重复提交同一命令只会得到已存在的状态。
* 状态迁移使用条件 UPDATE（`... WHERE command_id=? AND status=?`），并发或
  重试下只有一次迁移生效。
* 执行结果按 `attempt` 认领，迟到结果不覆盖状态。
* **动作处理器契约**：处理器可能因为超时回退或崩溃恢复而被再次调用，必须以
  `command_id` 作为下游系统的幂等键，自行保证重复调用安全。

## 乱序交互

审批按钮/消息操作可能先于命令消息到达：

1. 交互到达但命令不存在时，事件照常进入 `processed_events`，同时交互被写入
   `pending_interactions` 并返回 `"status": "buffered"`。
2. 命令随后到达并建单后，在同一事务内取出该命令的缓冲交互并立即内联重放，
   命令可直接从 `PENDING_APPROVAL` 推进到执行。
3. 缓冲交互本身也按 `event_id` 唯一，重复的早到交互不会被缓冲两次。

## 重启后的一致性

* 所有状态、去重记录、缓冲交互、审计都落在 SQLite（WAL）中，重启不丢失。
* 见 `docs/state-machine.md` 的“重启恢复对账”表：未完成的继续推进，终态
  命令绝不重复执行。
* 崩溃若发生在「副作用已发生但状态未持久」之间，恢复会再次调用幂等处理器，
  由处理器 + attempt 机制共同保证最终状态与副作用一致。

## 同 ID 重复建单

若不同 `event_id` 的命令消息引用了同一个已存在的 `command_id`，服务不会插入
第二条命令，也不会产生第二次副作用；响应为 `"status": "already_exists"` 并携带
该命令当前真实状态，审计记录 `command_resubmit_ignored`。
